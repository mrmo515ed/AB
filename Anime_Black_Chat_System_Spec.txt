ANIME BLACK — COMPLETE CHAT SYSTEM SPECIFICATION
=================================================

PURPOSE
-------
Build, repair, integrate, and fully connect the Anime Black chat system as ONE unified production system.
This document is a complete specification for the chat feature and its internal logic.

ABSOLUTE RULES
--------------
1. DO NOT delete, remove, replace, disable, downgrade, simplify, skip, hide, or break any existing feature, page, button, option, event, ID, route, component, API, backend connection, database field, or working behavior.
2. Existing features not explicitly mentioned in this document MUST remain intact and functional. They are reserved for future development.
3. Treat this document as an ADDITIVE + REPAIR + INTEGRATION specification, not a rewrite that removes existing functionality.
4. Before modifying code, inspect and understand the existing chat system, database, backend, models, navigation, screens, events, permissions, existing options, and current UI.
5. Preserve existing IDs, routes, database references, API contracts, event names, and public interfaces whenever possible. If a migration is necessary, provide compatibility instead of silently breaking old data.
6. Do not create mock data, fake persistence, fake realtime, fake uploads, fake GIFs, fake voice recording, or placeholder buttons where real functionality is expected.
7. Use the existing backend/database/server architecture already connected to the project. If Firebase is already used, keep Firebase. Do not replace the backend unless absolutely required and compatible.
8. Every newly implemented feature must be connected to the real backend/database/storage and realtime synchronization where applicable.
9. Test every modified feature and integration path. Do not finish with compile-only validation.
10. Fix the root cause, not only the visible symptom.

CORE ARCHITECTURE PRINCIPLE
---------------------------
The chat system must have ONE central message/conversation architecture.
Do not create independent sender/receiver/direction/sync logic for text, image, video, file, voice, GIF, sticker, location, contact, or other message types.

Central architecture:
Conversation Engine
    -> Message Engine
        -> Content / Attachment Engine
        -> Message Renderer
        -> Sync Engine
        -> Status / Reaction / Reply / Edit / Delete / Schedule logic

The same message engine decides:
- sender
- recipient/conversation
- isMine
- message direction
- alignment
- bubble style
- content type
- attachments
- status
- reactions
- reply
- edit/delete state
- scheduling state
- realtime synchronization
- deduplication
- ordering

- any other existing project message type

SENDER / RECEIVER / MESSAGE DIRECTION
-------------------------------------
Determine direction ONLY from message ownership, never from content type.

isMine = (message.senderId == currentUserId)

If isMine = true:
- render as sender/self message
- align to sender side according to the current language direction rules

If isMine = false:
- render as receiver/other-user message
- align to receiver side according to the current language direction rules

Apply the exact same ownership/direction logic to:
- text
- images
- video
- files
- voice
- GIF
- stickers
- location
- contact
- repost
- quote
- poll
- mixed attachments
- system-supported additional message types

Do NOT implement separate direction logic for different content types.

Support Arabic RTL and English LTR correctly.
Correct all direction-aware UI elements:

MESSAGE SENDING PIPELINE
------------------------
Every send operation should follow a stable flow:
1. Validate the message and permissions locally.
2. Create a clientMessageId before server submission.
3. Create an optimistic local pending message where appropriate.
4. Upload required attachments to real storage.
5. Create/update the server message with real metadata.
6. Receive the authoritative server messageId/timestamp.
7. Reconcile/replace the temporary local message instead of creating a duplicate.
8. Update conversation last-message metadata.
9. Update the UI without rebuilding the entire chat unnecessarily.
10. Realtime listeners must recognize the already-created message and not duplicate it.

MESSAGE DEDUPLICATION
---------------------
Every send must support idempotency/deduplication.
Use clientMessageId and/or the stable server messageId.
If a retry happens due to weak internet, the same logical message must not appear twice.

MESSAGE STATUS
--------------
Support the existing project's statuses and, where applicable:
- SENDING
- SENT
- DELIVERED
- READ
- FAILED
- SCHEDULED
- CANCELED

Failed messages must remain visible and offer retry when supported.
Retry must not create duplicates.

SCROLL SYSTEM
-------------
Build a smart scroll system.
Never reset or jump to the top when sending or receiving messages.

Rules:
- If the user is already near the bottom, new messages may auto-scroll to the newest message.
- If the user is reading older messages, do NOT move their viewport.
- Show a non-intrusive "new messages" indicator when appropriate.
- Sending a message must not cause a visible flicker or reset.
- Loading older messages must preserve the user's visible position.
- Navigating to a reply/search result should scroll to the target message and preserve context.
- Do not recreate the entire message list unnecessarily.

For pagination:
- Use cursor/page based loading.
- Load a reasonable initial batch.
- Load older messages on demand.
- When prepending older messages, preserve the current anchor/visible item position.

ORDERING
--------
Use authoritative server timestamps or server ordering.
When multiple messages arrive rapidly, sort deterministically using server time plus a stable tie-breaker such as messageId or sequence.
Do not rely only on the device clock.

- any existing text formatting currently in the project

REPLY SYSTEM

Display a compact preview of the replied-to message.
Pressing the reply preview should navigate/scroll to the original message.
Reply must work consistently with text, media, voice, GIF, sticker, file, location, contact, and other supported types.

If a user cancels reply mode, only reply state is cleared; the original message remains unchanged.

------------------------------
Double tap should trigger the configured quick reaction when enabled.
Long press should open the reaction/action menu.
Support configurable reactions according to existing project settings.
A user reaction should be toggled/changed instead of creating uncontrolled duplicates.
Reactions must sync in realtime when supported.

ATTACHMENT ARCHITECTURE

- contact metadata

MULTIPLE ATTACHMENTS IN ONE MESSAGE
------------------------------------
A single send action must create ONE message when the user intentionally selects multiple attachments for one message.
Example:
5 images + caption = 1 message with 5 attachments + text.

Do NOT send:
image1 = message 1
image2 = message 2
image3 = message 3
image4 = message 4
image5 = message 5

Instead:
Message
  attachments = [image1, image2, image3, image4, image5]
  text = caption

The same principle should be used for any combination of attachment types that the current project explicitly supports in one message.
